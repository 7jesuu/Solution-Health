# Системные проблемы и риски запуска мобильного приложения «Здоровье+»

| Проблема | Признаки | Влияние на приложение |
|----------|----------|-----------------------|
| **Отсутствие идемпотентности в системе Расписания** | Дубли записей при повторных POST (пациент дважды нажал «Записаться»). Jira INT-005 (Blocker), SD-003, отзыв Дмитрия (техлид расписания), отзыв Олега (каждый второй звонок — «записался онлайн, а меня не приняли»). | Невозможность надёжной онлайн-записи: дубли слотов, конфликты, эскалации в кол-центр. MVP не сможет снизить нагрузку на контакт-центр на 30 %. При росте до 50 000 пользователей — массовые сбои и репутационные потери. |
| **Ненадёжность платёжного шлюза и отсутствие корректной обработки таймаутов** | При таймауте деньги списываются, статус платежа не фиксируется; двойные списания. Jira INT-001 (Blocker), SD-002, SD-004, SD-009, отзыв Марины (акция «Скидка 10 %» привела к двойным списаниям и сворачиванию), новости о потерянных оплаченных записях. | Критический риск для сценария оплаты: потеря денег, невозможность подтверждения записи, возвраты неделями. MVP с оплатой будет генерировать жалобы и убытки; бизнес боится запускать любые акции, связанные с оплатой. |
| **Нестабильность и низкая масштабируемость 1С (полисы)** | Ошибки 503 при >50 rps, ответы >30 сек, «Полис недействителен» (null), контракт меняется без уведомлений (JSON → XML), нет rate limiting. Jira INT-003 (Critical), SD-001, SD-008, отзывы Анны и Алексея. | Блокировка сценария «Управление полисами ДМС» и онлайн-записи по ДМС. При пиковой нагрузке 500+ пользователей проверка полиса будет падать → отказ в записи. Финальная цель 50 000 пользователей недостижима без кардинальной переработки. |
| **Ненадёжная интеграция LIS → CRM (FTP + REST на старом Perl)** | FTP падает с 425/таймаутами, нет автоматических повторов, задержки до 2 часов, дубли XML-файлов, данные «застревают» в очереди. Jira INT-002, INT-008, INT-011, SD-005, отзывы Елены, Анны, Алексея. | Невозможность сценария «Получение результатов анализов без звонка». Пациенты не видят анализы в приложении вовремя → звонки в кол-центр, недовольство. Врачи тоже не видят актуальные данные. |
| **Хрупкость и отсутствие масштабирования RabbitMQ (уведомления)** | Очереди переполняются в пики (вечер понедельника), ошибка 404, пользователи не получают уведомления о записях. Сервис уведомлений висит на том же брокере. Jira INT-004, SD-006, отзыв Елены. | Сбой push/SMS/email о статусе записи, готовности анализов и акциях. Один из ключевых сценариев MVP (уведомления) будет нестабилен. При росте нагрузки до 50 000 пользователей — массовая потеря сообщений. |
| **Блокировки и отсутствие read-реплик в БД Расписания** | В часы пик блокировки на таблице слотов; изменения врачей вносятся с задержкой или не сохраняются. Jira INT-009, отзыв Дмитрия, новости («врачи перегружены, система расписания не справляется»), отзыв Олега. | Медленная работа записи и управления расписанием. При 500 одновременных пользователях (MVP) и тем более 50 000 — деградация производительности, таймауты, невозможность достичь <1 с ответа для 99 % запросов. |
| **Отсутствие observability (distributed tracing) и слабая отказоустойчивость интеграций** | Сложно найти корень сбоя при проблемах между системами. Jira INT-007 (Critical). Ручные перезапуски коннекторов, отсутствие автоповторов. | Долгий поиск и устранение инцидентов в production. При запуске MVP любые сбои интеграций будут «чёрным ящиком», что сделает невозможным соблюдение SLA 99,95 % и быстрое реагирование. |
| **Устаревшие и небезопасные компоненты (веб-портал + legacy)** | SQL-инъекция в поиске пациента (Jira INT-006), возможная подмена сессии (SD-007), медленная работа портала, ручной ввод в Excel врачами. | Риски безопасности данных пациентов при интеграции мобильного приложения через существующие API. Репутационные и регуляторные риски (персональные данные). Портал как текущий «фасад» не выдержит нагрузку и не может быть надёжной основой для мобильного API. |
| **Общая фрагментарность архитектуры и отсутствие API Gateway с rate limiting / идемпотентностью** | Часть систем — микросервисы (Расписание, CRM), часть — legacy (1С, LIS на SOAP/FTP/Perl). Нет единого шлюза. Jira INT-010 (Epic Critical), отзывы сотрудников, диаграмма C4. | Невозможность безопасного и масштабируемого подключения мобильного приложения. Без API Gateway с rate limiting и идемпотентностью пиковая нагрузка 500 (а тем более 50 000) пользователей приведёт к каскадным отказам всех backend-систем. |

## Ключевые выводы

**Для MVP (через 3 месяца)**  
Без устранения проблем с идемпотентностью записи, платежами, 1С и уведомлениями MVP не сможет обеспечить даже базовые сценарии (запись + оплата + уведомления) и снизить нагрузку на кол-центр. Риск провала запуска очень высокий.

**Для финального решения (через год)**  
Необходимы: API Gateway, идемпотентность всех критических операций, read-реплики и горизонтальное масштабирование, замена/изоляция legacy (1С, FTP-интеграции LIS), полноценный observability и гарантированная доставка уведомлений. В противном случае цели по 70 % онлайн-записи, 50 000 пользователей и SLA 99,95 % недостижимы.
