# Надёжная поставка результатов анализов в мобильное приложение

## Текстовое описание решения

Текущий процесс (LIS → FTP/SOAP → ненадёжный Perl-коннектор → REST → CRM) является главным источником проблем: потери файлов, дубли, задержки до 2 часов, отсутствие ретраев и идемпотентности. Пациенты не видят результаты онлайн, врачи работают с устаревшими данными, кол-центр перегружен.

**Выбранное архитектурное решение** — ввести выделенный **Results Ingestion Service** (микросервис на Java/Spring Boot в том же стеке, что CRM и Расписание) + использование **Apache Kafka** (или улучшенный RabbitMQ с durable queues + DLQ, но Kafka предпочтительнее для пиковых нагрузок и гарантированной доставки) как центральной шины событий.

### Ключевые принципы

1. **Гарантированная доставка (at-least-once + идемпотентность)**
   - LIS (или лёгкий адаптер рядом с ним) публикует событие `AnalysisResultReady` в Kafka-топик `lab.results` сразу после готовности результата (вместо прямой передачи в CRM).
   - Сообщение содержит: `resultId` (уникальный), `patientId`, `orderId`, `timestamp`, `payload` (результаты), `idempotencyKey` (hash от resultId + version).
   - Consumers (Ingestion Service) обрабатывают с `exactly-once` семантикой внутри сервиса (транзакции + проверка идемпотентности в PostgreSQL).
   - Dead Letter Queue + автоматические ретраи с экспоненциальной задержкой.
   - Acknowledgments только после успешной записи в CRM и отправки уведомления.

2. **Минимальная задержка**
   - Цель end-to-end < 30–60 секунд в 99 % случаев (вместо текущих часов).
   - Ingestion Service обновляет CRM (через существующий REST) и параллельно кладёт данные в кэш (Redis) для быстрого чтения приложением.
   - Сразу после успешной записи публикуется событие `ResultAvailable` в топик уведомлений → Notifications-сервис (RabbitMQ) отправляет push/SMS.

3. **Поддержка пиковой нагрузки** (до 50 000 пользователей, 500 concurrent сейчас, рост)
   - Kafka с партиционированием по `patientId` / `clinicId`.
   - Горизонтальное масштабирование Ingestion Service и API Gateway.
   - Rate limiting + circuit breaker на стороне API.
   - Read-replicas PostgreSQL + Redis для чтения результатов пациентом.

4. **Простота эксплуатации**
   - Минимальные изменения в legacy-LIS (только публикация события или лёгкий sidecar/адаптер).
   - Полный observability: distributed tracing (добавить OpenTelemetry — решает INT-007), метрики (latency, lag Kafka, error rate), алерты.
   - Лаборанты по-прежнему только читают в LIS; управление процессом — через мониторинг очередей.
   - Идемпотентность и DLQ позволяют безопасно перезапускать.

### Поток для мобильного приложения

- Пациент авторизуется → API Gateway (с rate limiting и идемпотентностью — INT-010).
- Получает push «Результаты готовы».
- Приложение делает `GET /api/v1/patients/{id}/results` (данные из CRM + Redis-кэш).
- Результаты отображаются мгновенно. Повторные запросы безопасны.

Это решение закрывает боли из интервью (Елена, Алексей, Анна, Олег), баги INT-002, INT-008, INT-011, SD-005 и напрямую поддерживает цели MVP (результаты без звонка) и финальные SLA (latency < 1 с, 99.95 % availability).


## Таблица сравнения архитектурных вариантов

| Критерий / Вариант                          | 1. Прямой polling приложения → CRM/LIS | 2. Улучшение текущего FTP + Perl-коннектор + REST в CRM | 3. Event-driven на существующем RabbitMQ | **4. Event-driven на Kafka + Results Ingestion Service (выбранный)** |
|---------------------------------------------|----------------------------------------|---------------------------------------------------------|------------------------------------------|---------------------------------------------------------------------|
| **Гарантированная доставка**                | Низкая (клиент может не запросить)     | Средняя (нужны ручные доработки ретраев)                | Высокая (при правильной конфигурации durable + DLQ) | **Очень высокая** (партиции, offset, exactly-once, DLQ из коробки) |
| **Задержка (p99)**                          | Высокая (зависит от частоты polling)   | 10–120 мин (как сейчас)                                 | 10–60 с                                  | **< 30–60 с**                                                       |
| **Пиковая нагрузка**                        | Плохо (нагрузка на CRM растёт линейно) | Средне                                                  | Хорошо (но RabbitMQ уже падает на пиках) | **Отлично** (горизонтальное масштабирование, 50k+ users)            |
| **Простота эксплуатации**                   | Высокая (минимум изменений)            | Низкая (старый Perl, ручные рестарты)                   | Средняя (уже есть, но нужна серьёзная настройка) | **Высокая** после внедрения (стандартный стек Java + Kafka)         |
| **Идемпотентность / дубли**                 | Нет                                    | Сложно добавить                                         | Можно                                    | **Встроена** (idempotencyKey)                                       |
| **Изменения в legacy**                      | Минимальные                            | Средние                                                 | Средние                                  | Минимальные (адаптер публикации)                                    |
| **Observability**                           | Слабая                                 | Слабая                                                  | Средняя                                  | **Полная** (tracing, lag, метрики)                                  |
| **Соответствие целям MVP + год**            | Не соответствует                       | Частично                                                | Хорошо для MVP                           | **Полностью** (масштабируемость на год вперёд)                      |
| **Риски**                                   | Высокая нагрузка на бэкенд, плохой UX  | Продолжение текущих инцидентов                          | Повторение проблем RabbitMQ              | Обучение команды Kafka (компенсируется выгодой)                     |
| **Рекомендация**                            | Отклонить                              | Временный патч                                          | Возможный компромисс                     | **Выбрать**                                                         |

**Обоснование выбора варианта 4**: он единственный одновременно даёт гарантированную доставку, низкую задержку, готовность к 50 000 пользователей и относительно простую эксплуатацию после внедрения. RabbitMQ можно оставить для уведомлений (как сейчас), а Kafka использовать только для критичного потока результатов.
