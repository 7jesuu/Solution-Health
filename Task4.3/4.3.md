# Проектирование базовых мер безопасности

## 1. Схема аутентификации пользователей мобильного приложения

Для мобильного приложения применяется схема **OAuth 2.0 + OpenID Connect** с использованием **JWT (JSON Web Token)**.

**Процесс:**

1. Пользователь вводит логин/пароль (или проходит вход через SMS-код / биометрию).
2. Мобильное приложение отправляет запрос на `/oauth/token` (Authorization Server).
3. В случае успеха сервер возвращает:
   - `access_token` (JWT, короткоживущий — 15–30 минут)
   - `refresh_token` (долгоживущий, хранится в Secure Storage устройства)
4. Все последующие запросы к API выполняются с заголовком:
5. При истечении `access_token` приложение прозрачно обновляет его с помощью `refresh_token`.
6. При компрометации или выходе пользователя оба токена отзываются (token revocation).

**Почему выбрано именно это решение:**
- JWT позволяет проверять токен без обращения к базе на каждый запрос (высокая производительность).
- Короткое время жизни access-токена снижает риск при его перехвате.
- Refresh-токен хранится только в защищённом хранилище устройства (Keychain / Keystore).
- Соответствует современным требованиям безопасности для медицинских приложений.

## 2. Политика Rate Limiting

| Тип запроса                        | Лимит                                      | Действие при превышении                          |
|------------------------------------|--------------------------------------------|--------------------------------------------------|
| Публичный: **Поиск врачей** (`GET /api/v1/doctors`) | 60 запросов в минуту с одного IP-адреса   | HTTP 429 Too Many Requests + Retry-After: 60     |
| Авторизованный: **Создание записи** (`POST /api/v1/bookings`) | 10 запросов в минуту на одного пользователя (по `sub` из JWT) | HTTP 429 Too Many Requests + временная блокировка возможности записи на 5 минут |

**Дополнительно:**
- На уровне API Gateway применяется скользящее окно (sliding window).
- При систематическом превышении лимитов IP/пользователь может быть временно занесён в блок-лист.

## 3. Обязательные меры защиты каналов передачи данных

1. **Только HTTPS (TLS 1.3)**  
   Все взаимодействие между мобильным приложением и backend происходит исключительно по TLS 1.3. Использование HTTP запрещено.

2. **Certificate Pinning**  
   В мобильном приложении реализуется pinning публичного ключа (или сертификата) сервера. Это защищает от MITM-атак даже при компрометации доверенных центров сертификации.

3. **Запрет передачи чувствительных данных в URL**  
   Токены, персональные и медицинские данные никогда не передаются в query-параметрах. Только в заголовках или теле запроса.

4. **Шифрование чувствительных полей на уровне приложения (дополнительный слой)**  
   Особенно критичные данные (например, результаты анализов) могут дополнительно шифроваться на клиенте перед отправкой (end-to-end или application-level encryption).

5. **HSTS и современные заголовки безопасности**  
   На стороне API Gateway принудительно включаются:
   - Strict-Transport-Security
   - Content-Security-Policy
   - X-Content-Type-Options
   - X-Frame-Options

6. **Валидация и санитизация всех входных данных**  
   Защита от SQL-инъекций, XSS и других инъекционных атак на уровне API Gateway и сервисов (уже выявленная SQL-инъекция в веб-портале не должна повториться).
